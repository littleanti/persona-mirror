## 1. 배경·목적

**Persona Mirror**(코드네임)는 카카오톡·문자 대화 기록으로 상대의 **페르소나와 말투**를 분석하고, 상대에게 받은 메시지에서 **"상대가 원하는 답변"** 을 추론해 **내 말투로 답변 후보 3개**를 제안하는 모바일 웹 앱이다.

우리가 풀려는 문제는 두 가지다.

1. **답장 고민** — "이 사람이 지금 이 말을 왜 했을까, 뭐라고 답해야 하나"를 혼자 판단하기 어렵다. 상대의 성격·관계 맥락을 반영한 답변 힌트가 필요하다.
2. **대화 기록은 가장 민감한 개인정보** — 위 문제를 풀려면 대화 원문을 LLM에 넣어야 한다. 그 대화가 운영자의 서버에 남는 구조는 사용자가 받아들이기 어렵고, 운영자도 보관 책임을 지고 싶지 않다.

그래서 이 제품의 설계 원칙은 한 줄로 고정한다.

> **개인정보는 개인 브라우저에, 연산은 사용자 키로, 서버는 정적 호스트.**

- 페르소나·대화·분석 기록은 **사용자 브라우저(IndexedDB)** 에만 저장한다.
- LLM 호출은 사용자가 직접 발급한 **Google AI Studio(Gemini) API 키**로 **브라우저가 Google에 직접** 요청한다.
- 서버는 빌드된 **정적 파일만** 서빙한다. API·DB·세션이 없다. (근거와 기각 대안은 §8)

표기: 코드네임은 "Persona Mirror", 패키지명은 `persona-mirror`. **정식 표시명은 M1(MVP) 전에 확정**한다(§11).

## 2. 대상 사용자·핵심 가치·사용 시나리오

### 2.1 대상 사용자
- 카카오톡/문자 대화에서 **상대의 의중을 파악하고 답장을 고민하는 일반 사용자**.
- **모바일 중심**: 대화 앱에서 텍스트를 복사해 바로 붙여넣고, 제안 답변을 복사해 되돌아간다. 데스크톱 브라우저도 동작하되 레이아웃은 모바일 폭 기준.
- 기술 전제: Google AI Studio에서 API 키를 발급받을 수 있는 사용자(온보딩에서 발급 링크를 안내한다).

### 2.2 핵심 가치
| 가치 | 설명 |
|---|---|
| 프라이버시 | 대화 원문이 우리 서버로 나가지 않는다. LLM 호출은 사용자 본인 키로 사용자 → Google 직접 통신. |
| 맞춤성 | 상대 페르소나뿐 아니라 **나의 페르소나(말투)** 도 함께 추출해, 답변을 내가 실제로 보낼 법한 말투로 만든다. |
| 비용·운영 | 운영자는 LLM 비용을 부담하지 않고, 서버는 정적 호스팅만 한다. |
| 이식성 | 정적 호스트 어디에나(GitHub Pages, 사내 정적 서버, 로컬 Node) 그대로 배포된다. |

### 2.3 사용 시나리오 (핵심 흐름)
| 단계 | 사용자 행동 | 시스템 동작 |
|---|---|---|
| S1 첫 진입 | 앱을 열고 Gemini API 키를 입력, 로컬 저장에 동의 | 키를 브라우저에 저장, 온보딩 모달 닫힘, 헤더에 "● Gemini 준비됨" 표시 |
| S2 대화 준비 | 카카오톡에서 상대와의 대화를 복사 | — |
| S3 페르소나 생성 | "페르소나" 탭 → 새 페르소나 → 상대 이름(+선택: 나의 이름) + 대화 붙여넣기 → 생성 | Gemini가 상대/나 페르소나 JSON을 생성, IndexedDB에 저장, 목록에 카드 추가 |
| S4 메시지 입력 | "분석하기" 탭 → 페르소나 선택 → 방금 받은 메시지 1건 붙여넣기 → 분석 | Gemini가 심리 분석 + 답변 후보 3개 생성 |
| S5 답장 | 마음에 드는 후보를 복사해 카카오톡에 붙여넣기 | 결과를 기록으로 저장 |
| S6 재조회 | "기록" 탭에서 과거 분석을 펼쳐 보거나 삭제 | IndexedDB 조회/삭제 |

S1은 최초 1회(또는 키 삭제 후)만 거친다. S3은 상대별 1회, S4~S5가 반복 사용의 중심이다.

## 3. 목표(G)·비목표(N)

### 3.1 목표
- **G1.** 3탭 모바일 SPA(페르소나 / 분석하기 / 기록)로 S1~S6 흐름을 완결한다.
- **G2.** 페르소나·분석 기록은 **IndexedDB**에만 저장하고 서버로 전송하지 않는다.
- **G3.** 첫 진입 시 Gemini API 키를 받아 브라우저에 저장하고, 키가 없으면 생성·분석 기능에 진입할 수 없게 한다.
- **G4.** 브라우저가 **Gemini API를 직접 호출**한다(대화 데이터가 우리 서버를 경유하지 않음).
- **G5.** 서버는 **빌드된 정적 자산만** 서빙한다(API/DB/세션 없음). 배포 대상은 GitHub Pages, 개발 중 미리보기는 로컬 Node 정적 서버.
- **G6.** TypeScript strict + 모듈 분리 + 빌드 게이트(`tsc --noEmit`, `vite build`)를 갖춘 소스 구조로 시작한다.
- **G7.** UI 문구는 한국어/영어를 전환할 수 있고, LLM 출력 언어도 선택 언어를 따른다.

### 3.2 비목표
- **N1.** 사용자 계정·로그인·클라우드 동기화(브라우저 로컬 한정).
- **N2.** 다중 LLM 공급자 추상화(이번 범위는 Gemini 단일). 단, 호출을 한 모듈에 캡슐화해 교체 비용은 낮게 유지한다.
- **N3.** 로컬 LLM(Ollama 등) 지원.
- **N4.** 서버 측 키 보관·프록시.
- **N5.** 메신저 앱 연동·대화 자동 수집(사용자가 복사·붙여넣기로 입력한다).

## 4. 기능 요구사항 (FR)

### 4.1 온보딩·API 키 관리
- **FR-1.** 앱 진입 시 저장된 키가 없으면 **온보딩 모달이 화면을 점유**한다. 모달 뒤의 탭·화면으로는 진입할 수 없다("나중에 하기" 없음).
- **FR-2.** 모달은 Gemini API 키 입력란과 **Google AI Studio 키 발급 링크**를 제공한다.
- **FR-3.** 저장 조건은 **키 입력 + "이 기기에만 저장됨" 동의 체크박스**다. 키가 비어 있거나 미동의면 토스트로 안내하고 저장하지 않는다.
- **FR-4.** 저장 전 **실시간 키 검증 호출은 두지 않는다.** 키의 유효성은 첫 생성/분석 호출의 인증 오류(403 등 — 분류 규칙은 [TRD §4.1](./TRD.md)) 처리로 드러나며, 그때 키 재입력을 유도한다.
- **FR-5.** 키는 브라우저 쿠키 `pm_gemini_key`(만료 1년, `SameSite=Lax`, HTTPS면 `Secure`)에 저장한다. 새로고침·재방문에도 유지된다. (선택 근거는 §8.4)
- **FR-6.** 키가 있으면 헤더 우측에 **"● Gemini 준비됨"** 인디케이터를 표시하고, 이를 눌러 키를 **변경/삭제**할 수 있다. 삭제하면 온보딩 모달이 다시 화면을 점유한다.

### 4.2 페르소나
- **FR-7.** 입력: **상대 이름(필수)** + **나의 이름(선택)** + **대화 텍스트(필수)**. 대화가 비어 있거나 너무 짧으면 토스트로 안내하고 호출하지 않는다. 거부 기준은 **공백 제거(trim) 후 20자 미만** — 임시값이며 근거 실측은 없다. 실사용 후 조정 여부는 §11.
- **FR-8.** 출력: 상대 페르소나 JSON. 나의 이름이 있으면 **상대 페르소나 + 나의 페르소나**를 동시에 추출한다. 페르소나 필드는 아래 11개다.

  | 필드 | 내용 |
  |---|---|
  | `summary` | 핵심 성격·관계 특성 요약(2~3문장) |
  | `communication_style` | 직접/간접, 솔직/우회, 감정/이성 등 소통 방식 |
  | `speech_level` | 반말/해요체/합쇼체 등 실제 어미 패턴 |
  | `vocabulary_examples[]` | 대화에서 실제로 등장한 단어·표현 인용(5개 이상) |
  | `sentence_style` | 문장 길이·구조 특징 + 실제 문장 예시 |
  | `emoji_symbol_usage` | 이모지·이모티콘·특수문자 사용 패턴 |
  | `texting_habits` | 메시지 길이, 띄어쓰기·맞춤법, 줄임말, 문장부호 버릇 등 말투 지문 |
  | `emotional_tendencies` | 감정 표현 방식(직접/암시, 강조 패턴) |
  | `what_they_value` | 대화에서 중시하는 가치 |
  | `how_they_seek_response` | 원하는 반응 유형과 그 밑의 정서적 욕구 |
  | `relationship_dynamics` | 이 관계에서의 역할·패턴 |

  `vocabulary_examples`·`sentence_style`·`texting_habits`는 **실제 발화를 그대로 인용**하도록 프롬프트가 강제한다. 나중에 이 말투를 재현해 답변을 쓰는 재료이기 때문이다.
- **FR-9.** 생성된 페르소나는 원본 대화와 함께 IndexedDB에 저장되고, **목록(최신순) / 상세 / 삭제**가 가능하다.
- **FR-10.** 상세 화면은 위 필드를 항목별로 보여주고, 나의 페르소나가 있으면 **상대 / 나 탭**으로 전환한다. LLM이 스펙에 없는 키를 추가로 돌려주더라도 UI는 깨지지 않고 관대하게 처리한다.
- **FR-11.** LLM 응답에서 JSON을 찾지 못한 경우(`extractJson`이 `{ raw }`를 돌려줌) 생성을 거부하지 않고 **원문을 보존해 저장**한다: 상대 페르소나 필드에 `raw` 원문이 들어가고, 목록 요약은 비며, 상세 화면에서 원문을 그대로 볼 수 있다. 사용자는 삭제 후 재시도한다. (P3 확정 — 근거는 [TRD §3.7](./TRD.md))

### 4.3 메시지 분석 v1
- **FR-12.** 입력: **저장된 페르소나 1개 선택** + **상대에게 받은 메시지 1건**(텍스트). 페르소나가 하나도 없으면 페르소나 탭으로 안내한다.
- **FR-13.** 출력: `analysis`(상대가 지금 느끼는 핵심 감정·진짜 욕구·이 메시지를 보낸 심리적 배경, 2~3문장) + **답변 후보 3개**. 후보는 모두 "감정을 먼저 알아주는 공감"을 기본으로 깔고, 공감 **이후**의 방향만 다르게 한다.

  | # | label | 방향 |
  |---|---|---|
  | 1 | 깊은 공감·수용형 | 감정에 더 깊이 머무르며 수용·지지 |
  | 2 | 공감 + 함께 해결형 | 공감 뒤 해결책·다음 행동을 함께 제안 |
  | 3 | 공감 + 분위기 전환형 | 공감 뒤 유머·온기로 분위기를 가볍게 |

  각 후보는 `{ label, reason, response }`로, `reason`은 "상대가 이 답변을 원하는 이유(어떤 감정/욕구를 채우는지)", `response`는 실제로 보낼 메시지 본문이다.
- **FR-14.** 페르소나에 **나의 페르소나**가 있으면 `response`는 **나의 실제 말투**(어미·길이·이모지·문장부호 버릇)로 작성한다. 공감을 이유로 말투를 바꾸지 않는다(짧은 반말이면 반말 안에서 공감). 나의 페르소나가 없으면 자연스러운 말투로 작성한다.
- **FR-15.** 프롬프트는 안티패턴을 금지한다: 섣부른 조언, 감정 축소("별거 아냐"), 진부한 위로, 질문 나열, 상대 감정 평가.
- **FR-16.** 각 후보에 **복사 버튼**을 두고, 복사 성공을 토스트로 알린다.
- **FR-17.** 분석 결과는 실행 즉시 **기록으로 자동 저장**된다(§4.4).
- **FR-18.** 호출 중에는 로딩 상태를 표시하고 중복 실행을 막는다. 네트워크 오류·인증 오류(403 등)·타임아웃(60초)·요청 과다(429)·서비스 일시 오류(5xx)·JSON 파싱 실패는 각각 구분된 토스트로 안내한다(분류 규칙은 [TRD §4.1](./TRD.md)).
- **FR-19.** LLM 응답이 JSON이 아니면 원문을 **후보 1개(`response`=원문)** 로 보존해 표시·저장한다. 사용자가 결과를 완전히 잃지 않게 하기 위함이다.

### 4.4 기록
- **FR-20.** 분석 기록을 **최신순 목록**으로 보여준다. 카드에는 상대 이름·일시·받은 메시지 요약을 표시한다.
- **FR-21.** 카드를 **펼치면** 분석 내용과 후보 3개를 보여준다. 복사는 분석 탭에서 수행하며, 기록 탭 후보 카드의 복사 버튼은 미확정(§11, [DESIGN §12](./DESIGN.md)).
- **FR-22.** 기록을 **삭제**할 수 있다. 페르소나를 삭제해도 그 페르소나로 만든 기록은 남는다(기록은 `persona_name`을 자체 보관한다).

### 4.5 상태 표시
- **FR-23.** 헤더 상태 인디케이터는 **키 등록 상태**를 나타낸다. 키가 있으면 "● Gemini 준비됨"을 모든 화면폭에서 표시하고(클릭 시 변경/삭제), 키가 없으면 온보딩 모달이 화면을 점유하므로 인디케이터는 렌더하지 않는다.
- **FR-24.** 사용자 피드백(저장·복사·오류)은 화면 하단 **토스트**로 통일한다. 토스트는 자동으로 사라진다.

### 4.6 다국어 (ko/en)
- **FR-25.** 헤더의 **한/EN 토글**로 UI 문구를 즉시 전환한다. 기본은 한국어.
- **FR-26.** 선택 언어는 LLM 출력에도 반영한다: 프롬프트 본문은 한국어로 유지하되, 영어 선택 시 **JSON 값은 영어로** 생성하도록 지시한다. **JSON 키는 언어와 무관하게 고정**한다(파싱 계약 보존).
- **FR-27.** 저장된 페르소나·기록은 생성 당시 언어 그대로 보관한다(재번역하지 않는다).

## 5. 데이터·프라이버시 요구사항 (DR)
- **DR-1.** 페르소나·분석 기록의 **모든 필드(원본 대화 포함)** 는 브라우저 IndexedDB에만 저장한다. DB 이름 `persona-mirror`, 스토어 `personas` / `analyses`.
- **DR-2.** API 키는 브라우저 쿠키 `pm_gemini_key`에 저장한다. 우리 서버는 정적 파일 서버이므로 키를 읽거나 저장하는 코드가 없다.
- **DR-3.** 우리 서버로 가는 네트워크 요청은 **정적 자산 요청만**이다. LLM 호출은 `generativelanguage.googleapis.com`으로 직접 나간다(검증: A3).
- **DR-4.** 페르소나 생성·메시지 분석 시 **입력한 대화 텍스트가 Google Gemini API로 전송**됨을 고지한다. 타인의 대화·민감정보 입력에 대한 주의도 함께 적는다. 기본안은 온보딩 모달이며, 노출 위치·문구 수준은 P2 온보딩 문구 작성 시 확정한다(§11).
- **DR-5.** 키·대화·프롬프트·LLM 응답을 **콘솔이나 서버 로그에 남기지 않는다.**
- **DR-6.** 사용자는 앱 안에서 **개별 페르소나·개별 기록·API 키**를 삭제할 수 있다. 브라우저 사이트 데이터 삭제 시 모든 로컬 데이터가 사라지고 복구 수단이 없음을 고지한다(고지 위치·문구는 DR-4와 함께 §11).
- **DR-7.** AI가 만든 페르소나와 답변 후보는 **참고용**이며 심리 진단이나 관계 결정을 대신하지 않음을 고지한다.

## 6. 비기능 요구사항 (NFR)
- **NFR-1. 모바일 우선.** 콘텐츠 최대 폭 `max-w-2xl`(672px) 중앙 정렬, 하단 탭바는 `max-w-lg`(512px) 중앙 고정, 터치 가능한 버튼 크기. 모바일(≤640px)에서는 두 값이 화면 폭과 같아 차이가 없고, 데스크톱에서는 페르소나 항목 카드·대화 입력란이 조금 더 넓게 놓인다(P3에서 `max-w-lg`→`max-w-2xl`로 조정).
- **NFR-2. 정적 산출물.** TypeScript strict, `npm run build` = `tsc --noEmit` + `vite build` → `dist/`. 런타임 Node 20+(빌드·미리보기 서버 기준).
- **NFR-3. 응답 지연.** 단일 모델 `gemini-3.1-flash-lite`에 `thinkingConfig.thinkingBudget=0`을 적용해 추론 토큰을 제거하고, 텍스트 요청 타임아웃은 60초로 둔다. **지연 수치는 미실측**(키 필요, §11).
- **NFR-4. 첫 로드 크기.** `@google/genai` 단일 SDK 사용, 불필요한 의존성 배제. SDK가 번들에 기여하는 크기는 M1 `vite build` 산출물에서 측정하며(미확정), 구체 상한도 그때 정한다(§11).
- **NFR-5. 오프라인 열람.** 저장된 페르소나·기록의 열람·삭제는 LLM 호출이 없으므로 네트워크 없이 동작해야 한다(앱 셸이 로드된 상태 기준).
- **NFR-6. 브라우저 지원.** 최신 iOS Safari, Android Chrome, 데스크톱 Chrome. IndexedDB 필수.
- **NFR-7. 보안 기본기.** 사용자 입력·LLM 출력은 React 텍스트 렌더링으로만 표시한다(HTML/Markdown 렌더 금지). CSP는 배포 단계(P7)에서 적용 예정.
- **NFR-8. 오류 복원력.** LLM 호출 실패가 앱 전체를 멈추지 않는다. 실패는 토스트로 알리고 입력값은 유지한다.

## 8. 아키텍처 방향 결정 (3단 사고)

### 8.1 문제
대화 원문을 LLM에 넣어야 하는 제품에서 **데이터(저장) · 연산(LLM) · 서버(호스팅)** 를 어디에 둘 것인가. 제약: 운영자는 개인 1인, LLM 비용을 상시 부담하기 어렵고, 사용자 대화를 보관하는 책임을 지고 싶지 않다. 배포는 가급적 정적 호스팅(GitHub Pages)으로 끝내고 싶다.

### 8.2 1차 사고 — 후보와 첫 결론
| 후보 | 데이터 | 연산 | 서버 | 첫인상 |
|---|---|---|---|---|
| (a) 서버 + 로컬 Ollama | 서버 디스크(JSON) | 서버의 로컬 LLM | 상시 앱 서버 + GPU | 외부 API 의존 없음, 비용 0에 가까움 |
| (b) 서버 프록시 + 운영자 키 | 서버 DB 또는 브라우저 | 서버가 운영자 키로 Gemini 호출 | 상시 API 서버 | 사용자가 키를 몰라도 됨, 온보딩 마찰 최소 |
| (c) Client-First | 브라우저 IndexedDB | 브라우저가 **사용자 키**로 Gemini 직접 호출 | 정적 파일만 | 서버 부담·비용·보관 책임 모두 0 |

1차 결론: **(c) Client-First.** (a)는 "사용자마다 서버와 GPU가 필요"해 배포 가능한 제품이 되지 않고, 대화가 서버 디스크에 남는다. (b)는 운영자 비용이 사용자 수에 비례하고, 대화가 운영자 인프라를 경유·보관될 수 있어 §1의 원칙과 충돌하며, 정적 호스팅이 불가능하다.

### 8.3 비판적 재사고 — (c)를 공격한다
| 공격 | 검토 | 결과 |
|---|---|---|
| **키가 브라우저에 있다(XSS 시 유출).** 서버 보관보다 위험하지 않은가? | 브라우저 JS가 Gemini를 직접 호출해야 하므로 키는 JS에서 읽을 수 있어야 한다(HttpOnly 불가). 이건 (c)의 구조적 비용이다. 완화는 두 층이다 — **주입 경로 차단**: 사용자·LLM 출력은 React 텍스트 렌더링만, 의존성 최소화, CSP(P7), 콘솔 미출력. **피해 범위 축소**: 키를 Gemini API(Generative Language API)만 쓰도록 제한하고 노출 의심 시 회전하도록 안내. HTTP referrer 제한은 AI Studio에서 가능한지 미확인이고, 성립해도 우리 origin에서 실행되는 XSS는 같은 referrer로 통과하며 탈취 후 비브라우저 클라이언트는 Referer를 임의로 넣을 수 있어 **효과가 제한적**이다. 키는 **사용자 소유**라 유출 시 피해 범위도 사용자 본인 키에 한정된다. | 살아남음(완화책 채택, 리스크 R1로 관리) |
| **사용자가 직접 키를 발급해야 한다.** 온보딩 마찰이 크지 않은가? | 대상 사용자를 "API 키를 발급받을 수 있는 사용자"로 명시(§2.1)하고, 발급 링크와 체크박스만으로 단순화한다. (b)로 마찰을 없애면 §1 원칙과 비용 구조가 무너진다. 이 트레이드오프는 의도적으로 감수한다. | 살아남음(대상 사용자 정의로 흡수) |
| **브라우저에서 Gemini를 직접 호출할 수 있는가(CORS)?** | `@google/genai`는 브라우저 사용을 지원하는 SDK다. CORS 통과 여부와 SDK 오류 객체의 형태는 **실키 없이도 확인할 수 있다** — 임의(무효) 키로 1회 호출하면 요청이 Google에 도달할 경우 인증 오류(400/403)가 SDK 오류로 돌아오고, CORS 차단이면 `Failed to fetch`/TypeError가 온다. P2에서 이 호출을 실행해 결과를 LOG에 기록하고, 실행하지 않았으면 미실행으로 남긴다. 실키가 필요한 항목은 품질·지연만이다. SDK 파손·브라우저 번들 미지원에 대비해 호출은 한 모듈에 캡슐화한다(REST 폴백은 R2a). | 살아남음(미확정 — P2 임의 키 호출로 확인) |
| **브라우저 데이터는 사라진다.** 사이트 데이터 삭제·기기 변경 시 복구 불가 | (a)/(b)처럼 서버에 두면 해결되지만 그것이 바로 피하려는 것이다. 고지(DR-6)한다. 유실에 대한 추가 대응책은 실사용 후 판단한다. | 살아남음(고지로 완화) |
| **(a)를 너무 쉽게 버렸나?** 서버 저장을 암호화하면 되지 않나 | 암호화해도 "사용자마다 GPU 서버가 필요"라는 배포 장벽은 그대로다. 이 제품의 대상은 일반 사용자(§2.1)이므로 (a)는 데모 이상이 되기 어렵다. | 기각 유지 |
| **(b)를 너무 쉽게 버렸나?** 서버리스 함수로 프록시하면 정적 호스팅에 가깝지 않나 | 호스팅 형태는 해결되지만 운영자 키·비용, 대화가 운영자 인프라를 경유한다는 점, 남용 방어(레이트리밋·인증)를 운영자가 떠안는 점은 그대로다. | 기각 유지 |
| **서버가 없으니 남용을 막을 수 없다.** | 호출 비용은 사용자 본인 키로 사용자에게 귀속되므로 운영자가 방어할 대상이 없다. | 살아남음 |

### 8.4 종합 — 결정
**Client-First를 채택한다.** 개인 데이터는 IndexedDB, LLM은 사용자 키로 브라우저 직접 호출, 서버는 정적 파일만(GitHub Pages 예정, 개발 중에는 로컬 Express 미리보기 서버로 같은 Wi-Fi 휴대폰 테스트). 살아남은 이유는 "대안들이 해결하는 문제(온보딩 마찰·데이터 유실)가 이 제품이 지키려는 원칙(보관 책임 없음·비용 0·정적 배포)보다 작다"는 것이다. 감수하는 비용은 XSS 노출면(R1)과 온보딩 마찰이며, 둘 다 완화책이 있다.

| 기각 대안 | 기각 이유 |
|---|---|
| (a) 서버 + 로컬 Ollama | 사용자마다 상시 서버·GPU 필요, 대화가 서버 디스크에 남음 |
| (b) 서버 프록시 + 운영자 키 | 운영자 비용이 사용자 수에 비례, 개인정보가 운영자 인프라를 경유·보관, 정적 호스팅 불가 |

**부속 결정 1 — 키 저장 매체(쿠키).**
- 1차 사고: 브라우저 쿠키 `pm_gemini_key`(1년, `SameSite=Lax`). 구현이 단순하고 새로고침·재방문에 유지되며, 만료를 선언적으로 둘 수 있다.
- 비판적 재사고: localStorage와 비교해 XSS 관점에서 더 위험한가? 둘 다 같은 origin의 JS에서 읽히므로 **XSS 관점의 노출면은 동등**하다고 판단했다(HttpOnly는 브라우저가 키를 써야 하므로 어차피 불가). 키 길이는 수십 자라 쿠키 크기 한도와 무관하다.
- 종합: **쿠키 채택.**

**부속 결정 2 — 모델.**
- 1차 사고: `gemini-3.1-flash-lite` 단일 모델 + `thinkingBudget=0`. flash 계열 중 thinking을 끌 수 있어 단건 지연을 줄일 수 있고(문헌 근거 — 지연 단축 효과는 미실측), 멀티모달이라 P5의 캡처 이미지 입력도 같은 경로로 처리 가능하다.
- 비판적 재사고: ① lite 모델이 한국어 대화의 뉘앙스 분석에 충분한가? thinking을 끄면 분석 깊이가 떨어지지 않는가? — 프롬프트가 필드·후보 구조를 강하게 지정하므로 자유 추론 의존도는 낮다고 가정하지만, **품질·지연 모두 키가 있어야 측정 가능**하다. ② 왜 lite인가? 비-lite flash도 thinking을 끌 수 있다. lite를 고른 근거(비용·무료 할당량·지연)는 실측이 없어 **선택 근거 미확정**이다. ③ 모델명과 `thinkingConfig` 자체가 API에서 수락되는지도 미확인이다.
- 종합: 채택하되 모델명·thinking 설정은 설정 파일 한 곳에서 관리해 실측 후 교체 가능하게 한다. P3~P4 실사용에서 품질 문제가 보이면 비-lite flash가 교체 후보다. 품질·지연·모델명 유효성은 미확정(§11).
