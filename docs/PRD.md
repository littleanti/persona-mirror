## 1. 배경·목적

**Persora**(초기 코드네임 Persona Mirror)는 카카오톡·문자 대화 기록으로 상대의 **페르소나와 말투**를 분석하고, **최근 대화 맥락에서 상대의 마지막 메시지**에 **내가 원하는 방향으로** 보낼 **답변 후보 3개**를 내 말투로 제안하는 모바일 웹 앱이다.

이 흐름은 세 레이어로 이뤄진다. **① 장기 페르소나** — 과거 대화로 상대(와 나)의 성격·말투를 한 번 파악해 저장한다. **② 단기 맥락** — 지금 진행 중인 최근 대화 몇 줄을 그때그때 넣는다. **③ 맞춤 답장** — 상대의 마지막 메시지에, 내가 지정한 답장 의도대로 답을 만든다. 세 레이어를 모두 입력 계약에 두는 것이 이 제품의 핵심이며, 그 근거는 §8 부속 결정 4에 있다.

우리가 풀려는 문제는 두 가지다.

1. **답장 고민** — "이 사람이 지금 이 말을 왜 했을까, 뭐라고 답해야 하나"를 혼자 판단하기 어렵다. 상대의 성격·관계 맥락을 반영한 답변 힌트가 필요하다.
2. **대화 기록은 가장 민감한 개인정보** — 위 문제를 풀려면 대화 원문을 LLM에 넣어야 한다. 그 대화가 운영자의 서버에 남는 구조는 사용자가 받아들이기 어렵고, 운영자도 보관 책임을 지고 싶지 않다.

그래서 이 제품의 설계 원칙은 한 줄로 고정한다.

> **개인정보는 개인 브라우저에, 연산은 사용자 키로, 서버는 정적 호스트.**

- 페르소나·대화·분석 기록은 **사용자 브라우저(IndexedDB)** 에만 저장한다.
- LLM 호출은 사용자가 직접 발급한 **Google AI Studio(Gemini) API 키**로 **브라우저가 Google에 직접** 요청한다.
- 키는 같은 브라우저의 **localStorage**에 둔다. 쿠키가 아니다 — 쿠키는 같은 사이트로 가는 모든 요청에 자동으로 실려 정적 호스트가 키를 받게 되기 때문이며, 그 사실은 실측으로 확인했다(§8 부속 결정 1).
- 서버는 빌드된 **정적 파일만** 서빙한다. API·DB·세션이 없다. (근거와 기각 대안은 §8)

표기: 표시명은 **Persora**(한·영 단일 표기), 패키지명은 `persora`. 초기 코드네임 "Persona Mirror"는 M1 직전에 Persora로 통일했다(근거: 360px 폭 헤더에서 두 단어 이름이 잘림 — [LOG](./LOG.md) 표시명 항목). IndexedDB 이름 `persona-mirror`는 코드네임 시절 로컬 데이터와의 호환을 위해 유지한다.

## 2. 대상 사용자·핵심 가치·사용 시나리오

### 2.1 대상 사용자
- 카카오톡/문자 대화에서 **상대의 의중을 파악하고 답장을 고민하는 일반 사용자**.
- **모바일 중심**: 대화 앱에서 텍스트를 복사해 바로 붙여넣고, 제안 답변을 복사해 되돌아간다. 데스크톱 브라우저도 동작하되 레이아웃은 모바일 폭 기준.
- 기술 전제: Google AI Studio에서 API 키를 발급받을 수 있는 사용자(온보딩에서 발급 링크를 안내한다).

### 2.2 핵심 가치
| 가치 | 설명 |
|---|---|
| 프라이버시 | 대화 원문이 우리 서버로 나가지 않는다. LLM 호출은 사용자 본인 키로 사용자 → Google 직접 통신. |
| 맞춤성 | 상대 페르소나뿐 아니라 **나의 페르소나(말투)** 도 함께 추출해, 답변을 내가 실제로 보낼 법한 말투로 만든다. |
| 비용·운영 | 운영자는 LLM 비용을 부담하지 않고, 서버는 정적 호스팅만 한다. |
| 이식성 | 정적 호스트 어디에나(GitHub Pages, 사내 정적 서버, 로컬 Node) 그대로 배포된다. |

### 2.3 사용 시나리오 (핵심 흐름)
| 단계 | 사용자 행동 | 시스템 동작 |
|---|---|---|
| S1 첫 진입 | 앱을 열고 Gemini API 키를 입력, 로컬 저장에 동의 | 키를 브라우저에 저장, 온보딩 모달 닫힘, 헤더에 "● Gemini 준비됨" 표시 |
| S2 대화 준비 | 페르소나용으로는 카카오톡에서 대화를 복사하거나 **대화 내보내기로 받은 .txt 파일**을 준비한다. 분석용 최근 대화는 복사하거나, 복사할 수 없으면 대화 화면을 캡처한다 | — |
| S3 페르소나 생성 | "페르소나" 탭 → 새 페르소나 → 상대 이름(+선택: 나의 이름) + **대화 붙여넣기 또는 카카오톡 대화 파일(.txt) 첨부** → 생성 | 첨부한 파일은 머리말을 떼고 **말미 일부만** 잘라 입력란을 채운다(FR-7). Gemini가 상대/나 페르소나 JSON을 생성, IndexedDB에 저장, 목록에 카드 추가 |
| S4 최근 대화 입력 | "분석하기" 탭 → 페르소나 선택 → **최근 대화 몇 줄을 그대로 붙여넣기**(텍스트 모드) → 앱이 답장할 마지막 메시지를 자동으로 잡아 보여줌(틀리면 직접 고름). 붙여넣을 수 없으면 **대화 화면 캡처를 첨부**(이미지 모드) | 텍스트 모드는 스레드를 화자별로 파싱해 상대의 마지막 발화를 답장 대상으로 표시. 이미지 모드는 파싱 없이 캡처를 그대로 모델에 넘긴다(FR-39) |
| S5 의도 선택·분석 | 원하는 답장 방향(위로·함께 해결·가볍게 전환·정중한 거절·선 긋기·설득·직접 입력)을 고르거나 비워 둔 채 분석 | Gemini가 심리 분석 + 답변 후보 3개 생성 |
| S6 답장 | 마음에 드는 후보를 복사해 카카오톡에 붙여넣기 | 결과를 기록으로 저장 |
| S7 재조회 | "기록" 탭에서 과거 분석을 펼쳐 보거나 삭제 | IndexedDB 조회/삭제 |

S1은 최초 1회(또는 키 삭제 후)만 거친다. S3은 상대별 1회, S4~S6이 반복 사용의 중심이다. S4에서 붙여넣은 대화는 페르소나별로 자동 저장되어 다음 방문에 그대로 복원된다(FR-32).

## 3. 목표(G)·비목표(N)

### 3.1 목표
- **G1.** 4탭 모바일 SPA(페르소나 / 분석하기 / 기록 / 설정)로 S1~S7 흐름을 완결한다. 설정 탭이 늘어난 것은 **목표가 바뀐 것이 아니다** — S1~S7은 그대로이고, 이미 있던 요구(DR-4·DR-6·DR-7 고지, DR-6의 데이터 삭제)를 사용자가 찾아갈 수 있는 자리에 놓은 것이다(§4.7).
- **G2.** 페르소나·분석 기록은 **IndexedDB**에만 저장하고 서버로 전송하지 않는다.
- **G3.** 첫 진입 시 Gemini API 키를 받아 브라우저에 저장하고, 키가 없으면 생성·분석 기능에 진입할 수 없게 한다.
- **G4.** 브라우저가 **Gemini API를 직접 호출**한다(대화 데이터가 우리 서버를 경유하지 않음).
- **G5.** 서버는 **빌드된 정적 자산만** 서빙한다(API/DB/세션 없음). 배포 대상은 GitHub Pages 프로젝트 사이트 `https://littleanti.github.io/persora/`, 개발 중 미리보기는 로컬 Node 정적 서버.
- **G6.** TypeScript strict + 모듈 분리 + 빌드 게이트(`tsc --noEmit`, `vite build`)를 갖춘 소스 구조로 시작한다.
- **G7.** UI 문구는 한국어/영어를 전환할 수 있고, LLM 출력 언어도 선택 언어를 따른다.

### 3.2 비목표
- **N1.** 사용자 계정·로그인·클라우드 동기화(브라우저 로컬 한정).
- **N2.** 다중 LLM 공급자 추상화(이번 범위는 Gemini 단일). 단, 호출을 한 모듈에 캡슐화해 교체 비용은 낮게 유지한다.
- **N3.** 로컬 LLM(Ollama 등) 지원.
- **N4.** 서버 측 키 보관·프록시.
- **N5.** 메신저 앱 연동·대화 자동 수집(사용자가 복사·붙여넣기로 입력한다).
- **N6.** **페르소나 자동 갱신.** 분석할 때마다 페르소나를 다시 계산하지 않는다. 페르소나는 만든 시점 그대로 정적으로 두고, 사용자가 필요할 때 "추가 대화로 업데이트"(FR-28)를 직접 실행한다. 근거는 §8 부속 결정 4.
- **N7.** **앱 안에서의 대화 누적.** 주고받는 대화를 앱이 이어서 보관하지 않는다. 분석할 때마다 최근 대화를 붙여넣는다. 재입력 부담은 페르소나별 드래프트 자동 저장(FR-32)으로만 낮춘다.

## 4. 기능 요구사항 (FR)

### 4.1 온보딩·API 키 관리
- **FR-1.** 앱 진입 시 저장된 키가 없으면 **온보딩 모달이 화면을 점유**한다. 모달 뒤의 탭·화면으로는 진입할 수 없다("나중에 하기" 없음).
- **FR-2.** 모달은 Gemini API 키 입력란과 **Google AI Studio 키 발급 링크**를 제공한다.
- **FR-3.** 저장 조건은 **키 입력 + 동의 체크박스**다. 동의 문구(`onboarding.consent`)는 "대화 내용이 Gemini API로 전송되고, 로컬 데이터는 브라우저 데이터 삭제나 기기 변경 시 복구할 수 없음을 이해했습니다."로, DR-4(Gemini 전송)·DR-6(복구 불가)을 함께 담는다 — 초안의 "이 기기에만 저장됨"은 P8에서 사실이 아님이 드러나 폐기했다(§8 부속 결정 1). 키가 비어 있거나 미동의면 토스트로 안내하고 저장하지 않는다.
- **FR-4.** 저장 전 **실시간 키 검증 호출은 두지 않는다.** 키의 유효성은 첫 생성/분석 호출의 인증 오류(403 등 — 분류 규칙은 [TRD §4.1](./TRD.md)) 처리로 드러나며, 그때 키 재입력을 유도한다.
- **FR-5.** 키는 브라우저 **localStorage** `pm_gemini_key`에 저장한다. 새로고침·재방문에도 유지되고, 브라우저 밖으로 나가지 않는다. 쿠키에 저장하던 구버전 키가 남아 있으면 **최초 읽기에서 한 번 localStorage로 옮기고 쿠키를 만료시킨다** — 옮기는 이유는 잔존 쿠키가 계속 요청 헤더에 실리기 때문이다. localStorage에 접근할 수 없는 환경(프라이빗 모드 등)에서는 현재 세션 메모리로만 키를 들고 있으며, 저장 실패로 앱을 멈추지는 않는다. (매체 선택 근거와 전환 경위는 §8.4 부속 결정 1)
- **FR-6.** 키가 있으면 헤더 우측에 **"● Gemini 준비됨"** 인디케이터를 표시하고, 이를 눌러 키를 **변경/삭제**할 수 있다. 삭제하면 온보딩 모달이 다시 화면을 점유한다.

### 4.2 페르소나
- **FR-7.** 입력: **상대 이름(필수)** + **나의 이름(선택)** + **대화 텍스트(필수)**. 대화 입력은 **하나뿐**이다 — 모드 토글이 없고, 화면에는 대화 입력란 하나와 그 위의 파일 첨부 버튼이 있다. 캡처 이미지 모드는 P10에서 제거했다(근거는 §8 부속 결정 3의 재검토).
  - **붙여넣기(기본 경로).** 대화 텍스트를 그대로 붙여넣는다. 비어 있거나 너무 짧으면 토스트로 안내하고 호출하지 않는다. 거부 기준은 **공백 제거(trim) 후 20자 미만** — 임시값이며 근거 실측은 없다. 실사용 후 조정 여부는 §11.
  - **카카오톡 대화 파일(.txt) 첨부.** 카카오톡의 "대화 내보내기"로 받은 텍스트 파일을 첨부하면 앱이 파일을 읽어 **같은 입력란을 채운다.** 채우기 전에 두 가지를 한다 — ① 내보내기 **머리말 제거**(예: "…님과 카카오톡 대화", "저장한 날짜 : …", "Date Saved : …", `--------------- YYYY년 M월 D일 … ---------------` 형태의 날짜 구분선). 머리말 패턴에 걸리지 않는 평범한 텍스트 파일은 원문을 그대로 통과시킨다. ② **말미(tail) 컷** — 파일이 상한(16,000자, [TRD §3.2](./TRD.md)의 `PERSONA_CHAT_TAIL_CHARS`)보다 길면 **가장 최근 쪽 16,000자만** 남기고 앞을 버린다. 최근 대화일수록 지금의 말투와 관계를 반영하기 때문이다. 자를 때 줄 중간에서 끊지 않고 **첫 줄바꿈 이후부터** 시작해 잘린 반쪽 줄은 버린다.
  - **화자 라벨과 타임스탬프는 지우지 않는다.** 모델이 누구의 발화인지 가르는 근거가 그것이기 때문이다.
  - 첨부 결과는 **사용자가 그대로 편집할 수 있다.** 채워진 텍스트는 일반 입력값이며, 앞부분을 더 붙이거나 필요 없는 구간을 지울 수 있다.
  - 첨부하면 **얼마나 쓰였는지 화면에 알린다** — 잘렸으면 "원본 N자 중 최근 M자만 사용", 잘리지 않았으면 "최근 M자 사용". 사용자가 직접 입력란을 고치면 이 안내는 사라진다(더 이상 첨부 결과 그대로가 아니므로).
  - **같은 파일을 다시 첨부할 수 있어야 한다.** 파일을 고른 뒤 입력란을 편집했다가 원본으로 되돌리는 흐름이 실제로 있기 때문이며, 구현 시 파일 입력값을 매번 비운다([TRD §3.10](./TRD.md)).
  - 첨부 파일을 읽지 못하면 토스트로 알리고 입력란은 건드리지 않는다.
  - 출력(FR-8)·저장(FR-9)·오류 처리(FR-11)는 붙여넣든 첨부하든 같다 — 어느 쪽이든 결국 입력란의 텍스트 하나가 전송되기 때문이다.
- **FR-8.** 출력: 상대 페르소나 JSON. 나의 이름이 있으면 **상대 페르소나 + 나의 페르소나**를 동시에 추출한다. 페르소나 필드는 아래 11개다.

  | 필드 | 내용 |
  |---|---|
  | `summary` | 핵심 성격·관계 특성 요약(2~3문장) |
  | `communication_style` | 직접/간접, 솔직/우회, 감정/이성 등 소통 방식 |
  | `speech_level` | 반말/해요체/합쇼체 등 실제 어미 패턴 |
  | `vocabulary_examples[]` | 대화에서 실제로 등장한 단어·표현 인용(5개 이상) |
  | `sentence_style` | 문장 길이·구조 특징 + 실제 문장 예시 |
  | `emoji_symbol_usage` | 이모지·이모티콘·특수문자 사용 패턴 |
  | `texting_habits` | 메시지 길이, 띄어쓰기·맞춤법, 줄임말, 문장부호 버릇 등 말투 지문 |
  | `emotional_tendencies` | 감정 표현 방식(직접/암시, 강조 패턴) |
  | `what_they_value` | 대화에서 중시하는 가치 |
  | `how_they_seek_response` | 원하는 반응 유형과 그 밑의 정서적 욕구 |
  | `relationship_dynamics` | 이 관계에서의 역할·패턴 |

  `vocabulary_examples`·`sentence_style`·`texting_habits`는 **실제 발화를 그대로 인용**하도록 프롬프트가 강제한다. 나중에 이 말투를 재현해 답변을 쓰는 재료이기 때문이다.
- **FR-9.** 생성된 페르소나는 **모델에 보낸 대화 텍스트 그대로**와 함께 IndexedDB에 저장되고, **목록(최신순) / 상세 / 삭제**가 가능하다. 파일을 첨부해 만든 페르소나도 저장되는 것은 입력란에 들어간 텍스트(머리말 제거·말미 컷을 거친 결과)이므로, 상세 화면에서 근거 대화를 그대로 되짚어 볼 수 있다. **첨부한 파일 자체는 저장하지 않는다** — 읽어서 입력란을 채우는 데만 쓴다. (P5~P9 동안 이미지 모드가 저장하던 캡처 장수 플레이스홀더는 P10에서 함께 사라졌다. 그 사이에 만든 기존 레코드에는 플레이스홀더 문자열이 남아 있을 수 있고, 화면은 그것을 **평범한 문자열로 그대로** 보여준다.)
- **FR-10.** 상세 화면은 위 필드를 항목별로 보여주고, 나의 페르소나가 있으면 **상대 / 나 탭**으로 전환한다. LLM이 스펙에 없는 키를 추가로 돌려주더라도 UI는 깨지지 않고 관대하게 처리한다.
- **FR-11.** LLM 응답에서 JSON을 찾지 못한 경우(`extractJson`이 `{ raw }`를 돌려줌) 생성을 거부하지 않고 **원문을 보존해 저장**한다: 상대 페르소나 필드에 `raw` 원문이 들어가고, 목록 요약은 비며, 상세 화면에서 원문을 그대로 볼 수 있다. 사용자는 삭제 후 재시도한다. (P3 확정 — 근거는 [TRD §3.7](./TRD.md))
- **FR-28.** **추가 대화로 업데이트.** 상세 화면에서 새로 나눈 대화를 붙여넣어 페르소나를 다시 만들 수 있다. 기존 원본 대화와 붙여넣은 대화를 **이어 붙여** 전체를 재분석하고, 같은 레코드를 덮어쓴다 — `id`와 생성일은 그대로 두고 갱신 시각만 새로 기록한다. 목록·기록에 걸린 참조가 끊기지 않게 하기 위함이다. 자동 갱신은 하지 않는다(N6). 대화가 비어 있으면 토스트로 안내하고 호출하지 않는다.

### 4.3 메시지 분석 v2 — 최근 대화 스레드 · 답장 대상 · 답장 의도

v1은 "받은 메시지 1건"만 받았고, 그래서 §1의 세 레이어 중 **② 단기 맥락**이 입력 계약에 없었다. v2는 그 자리를 채운다. 재설계의 3단 사고와 반증 실측은 §8 부속 결정 4에 있다.

- **FR-12(개정).** 입력: **저장된 페르소나 1개 선택** + **최근 대화**(필수) + **답장 의도**(선택). 최근 대화는 **텍스트 붙여넣기**와 **캡처 이미지 첨부** 두 모드 중 하나로 넣으며(FR-39), 기본은 텍스트다. 페르소나가 하나도 없으면 페르소나 탭으로 안내한다. 텍스트 모드에서 스레드가 공백이면, 이미지 모드에서 캡처가 0장이면 토스트로 안내하고 호출하지 않는다.
- **FR-13(개정).** 출력: `analysis`(상대가 지금 느끼는 핵심 감정·진짜 욕구 + **최근 대화 흐름 속에서** 이 마지막 메시지를 보낸 심리적 배경, 2~3문장) + **답변 후보 3개**. 후보의 세 갈래는 답장 의도의 유무로 갈린다.

  **의도를 비웠을 때(기본)** — v1과 같은 공감 3축을 그대로 쓴다. 이 경로는 v1에서 바뀌지 않는다.

  | # | label | 방향 |
  |---|---|---|
  | 1 | 깊은 공감·수용형 | 감정에 더 깊이 머무르며 수용·지지 |
  | 2 | 공감 + 함께 해결형 | 공감 뒤 해결책·다음 행동을 함께 제안 |
  | 3 | 공감 + 분위기 전환형 | 공감 뒤 유머·온기로 분위기를 가볍게 |

  **의도를 지정했을 때** — 세 후보가 모두 그 목표를 향하고, 접근 방식·톤·강도만 달라진다. 감정·욕구를 먼저 인정하는 순서는 그대로다.

  | # | label | 방향 |
  |---|---|---|
  | 1 | 부드럽고 완곡하게 | 지정한 목표를 완곡한 표현으로 |
  | 2 | 솔직하고 분명하게 | 지정한 목표를 직접적으로 |
  | 3 | 따뜻한 유머를 곁들여 | 지정한 목표를 유머·온기와 함께 |

  각 후보는 `{ label, reason, response }`로, `reason`은 "상대가 이 답변을 원하는 이유(어떤 감정/욕구를 채우는지)", `response`는 실제로 보낼 메시지 본문이다.
- **FR-29(텍스트 모드 전용).** **스레드 파싱과 답장 대상 자동 검출.** 붙여넣은 스레드를 화자별 줄로 파싱한다. 카카오톡 내보내기식 `[이름] [시간] 내용`을 1차로, `이름: 내용`을 폴백으로 인식하고, 화자 라벨을 페르소나의 상대 이름·나의 이름과 대조해 **나 / 상대 / 알 수 없음**으로 분류한다. 라벨이 없는 줄은 직전 발화의 이어짐으로 붙인다. 답장 대상은 **마지막 상대 발화**이며, 상대 발화를 찾지 못하면 마지막 비어 있지 않은 줄로 폴백한다. 검출한 대상은 화면에 **"이 메시지에 답장"** 으로 보여준다 — 앱이 무엇에 답하는지 사용자가 항상 볼 수 있어야 한다.
- **FR-30(텍스트 모드 전용).** **답장 대상 수동 교정.** 자동 검출이 틀렸을 때 사용자가 파싱된 줄 목록에서 다른 메시지를 직접 고를 수 있다. 목록은 각 줄의 화자와 본문 앞부분을 보여준다. 수동 지정은 그 분석에만 적용되고, 스레드를 다시 편집하면 자동 검출로 되돌아간다.
- **FR-31.** **답장 의도.** 프리셋 6종(위로·공감 / 함께 해결 / 가볍게 전환 / 정중한 거절 / 선 긋기 / 설득·제안)과 **직접 입력**을 제공한다. **비워 두는 것이 기본값**이며, 비어 있으면 FR-13의 공감 3축이 그대로 동작한다(v1 무회귀). 직접 입력은 자유 문장이며 그대로 프롬프트의 답장 목표가 된다.
- **FR-32(텍스트 모드 전용).** **스레드 드래프트 자동 저장·복원.** 붙여넣은 스레드는 **페르소나별로** 브라우저에 자동 저장되고, 그 페르소나를 다시 고르면 그대로 복원된다. 앱이 대화를 이어서 누적하지는 않으며(N7), 같은 대화를 다시 붙여넣는 수고만 덜어 준다. 저장소에 접근할 수 없는 환경(프라이빗 모드 등)에서는 조용히 저장을 건너뛰고 분석 자체는 그대로 동작한다. **첨부한 캡처는 드래프트로 저장하지 않는다** — 이미지를 브라우저 저장소에 쌓지 않는다는 FR-9·FR-40의 원칙을 그대로 따른다.
- **FR-14.** 페르소나에 **나의 페르소나**가 있으면 `response`는 **나의 실제 말투**(어미·길이·이모지·문장부호 버릇)로 작성한다. 공감을 이유로 말투를 바꾸지 않는다(짧은 반말이면 반말 안에서 공감). 나의 페르소나가 없으면 자연스러운 말투로 작성한다. 답장 의도를 지정해도 이 규칙은 그대로다.
- **FR-15.** 프롬프트는 안티패턴을 금지한다: 섣부른 조언, 감정 축소("별거 아냐"), 진부한 위로, 질문 나열, 상대 감정 평가.
- **FR-16.** 각 후보에 **복사 버튼**을 두고, 복사 성공을 토스트로 알린다.
- **FR-17.** 분석 결과는 실행 즉시 **기록으로 자동 저장**된다(§4.4).
- **FR-18.** 호출 중에는 로딩 상태를 표시하고 중복 실행을 막는다. 네트워크 오류·인증 오류(403 등)·타임아웃(60초)·요청 과다(429)·서비스 일시 오류(5xx)·JSON 파싱 실패는 각각 구분된 토스트로 안내한다(분류 규칙은 [TRD §4.1](./TRD.md)).
- **FR-19.** LLM 응답이 JSON이 아니면 원문을 **후보 1개(`response`=원문)** 로 보존해 표시·저장한다. 사용자가 결과를 완전히 잃지 않게 하기 위함이다.
- **FR-39.** **분석 입력 모드 토글(텍스트 / 캡처 이미지).** 최근 대화 입력란 위에 두 모드를 고르는 토글을 둔다. 기본은 텍스트이며 선택 근거는 §8 부속 결정 5다.
  - **텍스트 모드(기본).** 지금까지의 동작 그대로다 — 스레드 파싱(FR-29), 답장 대상 칩과 수동 교정(FR-30), 드래프트 저장·복원(FR-32)이 모두 여기서만 동작한다.
  - **캡처 이미지 모드.** 최근 대화 화면 캡처를 **여러 장** 첨부한다(`image/*`만). 첨부한 이미지는 썸네일로 보여주고 개별 제거할 수 있다. 이미지가 **0장이면** 토스트로 안내하고 호출하지 않는다. 캡처는 별도 OCR 없이 **멀티모달 모델이 이미지에서 대화를 직접 읽어** 분석하며, 말풍선의 좌/우 위치와 이름표로 화자를 구분하고 여러 장은 화면 순서(위→아래, 앞→뒤)대로 이어 해석하도록 지시한다.
  - **이미지 모드에서는 답장 대상을 앱이 표시하지 못한다.** 스레드 텍스트가 없어 파싱할 것이 없으므로, "이 메시지에 답장" 칩도 수동 교정 목록도 렌더하지 않는다. 그 대신 **맨 아래(최신)의 상대 메시지에 답장하라**는 지시를 프롬프트가 모델에게 직접 준다. 즉 이 모드에서 답장 대상을 고르는 주체는 앱이 아니라 모델이고, 모델이 잘못 고르면 **사용자가 고칠 수단이 없다.** 이것이 이 모드에서 감수하는 유일한 기능 후퇴이며, 관찰 항목으로 남긴다(§9 R10·§11).
  - 두 모드의 답장 의도(FR-31)·출력(FR-13)·기록 저장(FR-17)·오류 처리(FR-18·FR-19)는 같다. 의도 칩은 이미지 모드에서도 그대로 동작한다.
- **FR-40.** **이미지 모드 기록의 플레이스홀더 저장.** 캡처 이미지 모드에는 저장할 대화 텍스트도, 앱이 아는 답장 대상 문장도 없다. 그래서 기록의 답장 대상 자리에 **캡처 장수 플레이스홀더**(예: "[채팅 캡처 이미지 2장으로 분석한 답장]")를 넣어 기록 목록의 미리보기가 비지 않게 하고, 스레드 원문 자리는 비운다. 플레이스홀더는 **생성 당시 언어로 굳으며** 나중에 UI 언어를 바꿔도 번역하지 않는다(FR-27과 같은 규칙). **이미지 자체는 저장하지 않는다** — 분석 요청에만 쓰고 버린다(FR-9와 같은 이유).

### 4.4 기록
- **FR-20.** 분석 기록을 **최신순 목록**으로 보여준다. 카드에는 상대 이름·일시·**답장 대상 메시지** 요약을 표시한다.
- **FR-21.** 카드를 **펼치면** 분석 내용과 후보 3개를 보여준다. 복사는 분석 탭에서 수행하며, 기록 탭 후보 카드의 복사 버튼은 미확정(§11, [DESIGN §12](./DESIGN.md)).
- **FR-22.** 기록을 **삭제**할 수 있다. 페르소나를 삭제해도 그 페르소나로 만든 기록은 남는다(기록은 `persona_name`을 자체 보관한다).
- **FR-33.** 기록은 답장 대상 메시지 외에 **붙여넣은 스레드 원문**과 **그때 쓴 답장 의도**도 함께 보관한다. 나중에 "왜 이 답이 나왔나"를 되짚을 수 있어야 하기 때문이다. 세 값은 모두 **선택 필드**로 더해지므로 v1에서 만든 기존 기록은 그대로 읽히고 목록·펼침 화면도 깨지지 않는다. 캡처 이미지 모드로 만든 기록은 스레드 원문이 비고 답장 대상 자리에 플레이스홀더가 들어간다(FR-40) — 되짚을 재료가 그만큼 적다는 뜻이며, 캡처를 저장하지 않기로 한 결과다.

### 4.5 상태 표시
- **FR-23.** 헤더 상태 인디케이터는 **키 등록 상태**를 나타낸다. 키가 있으면 "● Gemini 준비됨"을 모든 화면폭에서 표시하고(클릭 시 변경/삭제), 키가 없으면 온보딩 모달이 화면을 점유하므로 인디케이터는 렌더하지 않는다. 여기서 지우는 것은 **키 하나**이고, 페르소나·기록까지 함께 지우는 수단은 설정 탭의 전체 삭제(FR-37)다 — 두 경로를 분리해 두어 키 교체가 데이터 삭제로 번지지 않게 한다.
- **FR-24.** 사용자 피드백(저장·복사·오류)은 화면 하단 **토스트**로 통일한다. 토스트는 자동으로 사라진다.

### 4.6 다국어 (ko/en)
- **FR-25.** 헤더의 **한/EN 토글**로 UI 문구를 즉시 전환한다. 기본은 한국어.
- **FR-26.** 선택 언어는 LLM 출력에도 반영한다: 프롬프트 본문은 한국어로 유지하되, 영어 선택 시 **JSON 값은 영어로** 생성하도록 지시한다. **JSON 키는 언어와 무관하게 고정**한다(파싱 계약 보존).
- **FR-27.** 저장된 페르소나·기록은 생성 당시 언어 그대로 보관한다(재번역하지 않는다).

### 4.7 설정·데이터 관리

브라우저 로컬에만 데이터를 두는 구조의 대가는 "유실되면 끝"과 "지울 방법이 앱 안에 있어야 한다"이다. DR-6·DR-7이 요구하던 것을 실제 화면으로 만든 자리가 설정 탭이다.

- **FR-34.** 하단 탭의 **네 번째 탭으로 설정**을 둔다. 자주 쓰지 않지만 **발견 가능해야 하는** 기능(백업·전체 삭제·고지)의 자리다.
- **FR-35.** **백업 내보내기.** 페르소나·분석 기록·스레드 드래프트를 JSON 한 파일로 내려받는다. 파일명에 내보낸 날짜를 담는다. **API 키는 넣지 않는다**(DR-8).
- **FR-36.** **백업 가져오기.** 내보낸 JSON 파일을 골라 로컬 데이터에 복원한다. **같은 `id`의 레코드는 덮어쓰고** 없는 레코드는 추가한다(지우지 않는 병합). 파일 형식이 맞지 않으면 토스트로 알리고 **아무것도 바꾸지 않는다.** 성공하면 복원한 페르소나·기록·드래프트 개수를 토스트로 알린다.
- **FR-37.** **전체 로컬 데이터 삭제.** API 키·페르소나·분석 기록·스레드 드래프트를 이 브라우저에서 한 번에 지운다. 되돌릴 수 없으므로 확인 대화상자를 거친다. 삭제하면 키가 없어지므로 온보딩 모달이 즉시 다시 화면을 점유한다.
- **FR-38.** **개인정보·면책 고지를 상시 노출한다.** 담을 내용은 여섯 가지다 — ① 페르소나·원본 대화·기록·드래프트는 이 브라우저(IndexedDB/localStorage)에 저장된다 ② 페르소나 생성·메시지 분석을 실행하면 입력한 대화 텍스트와 첨부한 캡처 이미지가 **Google Gemini API로 직접 전송**된다 ③ 키는 localStorage에 있으며 Google Cloud에서 **키의 사용 API를 Gemini API로 제한**할 것을 권한다 ④ 브라우저 데이터 삭제·시크릿 모드 종료·기기 변경 시 로컬 데이터는 **복구할 수 없다**(백업을 권함) ⑤ 타인의 대화·민감정보 입력에 주의할 것 ⑥ AI가 만든 페르소나와 답변 후보는 **참고용**이다(DR-7).
  - 이로써 DR-4·DR-6·DR-7 고지의 노출 위치가 확정된다: **온보딩 모달(최초 1회) + 설정 탭(상시)**. 온보딩은 진입을 막는 화면이라 문구가 짧아야 하고, 설정은 언제든 다시 읽을 수 있어야 하므로 항목을 다 편다.

## 5. 데이터·프라이버시 요구사항 (DR)
- **DR-1.** 페르소나·분석 기록의 **모든 필드(원본 대화 포함)** 는 브라우저 IndexedDB에만 저장한다. DB 이름 `persona-mirror`, 스토어 `personas` / `analyses`. 분석 탭에서 붙여넣은 **스레드 드래프트**(FR-32)만 예외적으로 localStorage에 페르소나별로 둔다 — 아직 분석하지 않은 임시 입력이라 레코드로 만들 대상이 아니기 때문이며, 같은 브라우저를 벗어나지 않는다는 점은 IndexedDB와 같다.
- **DR-2.** API 키는 브라우저 **localStorage** `pm_gemini_key`에 저장한다. 우리 서버는 정적 파일 서버이므로 키를 읽거나 저장하는 코드가 없고, **키가 요청에 실려 서버에 도달하는 경로도 없다.** 쿠키에 저장하던 동안에는 뒤 문장이 성립하지 않았다 — 근거와 실측은 §8 부속 결정 1.
- **DR-3.** 우리 서버(정적 호스트)로 가는 네트워크 요청은 **정적 자산 요청뿐이며, 그 요청에는 개인 데이터도 API 키도 실리지 않는다.** LLM 호출은 `generativelanguage.googleapis.com`으로 직접 나간다(검증: A3). 이 문장은 키 저장소를 localStorage로 옮긴 뒤에야 사실이 된다.
- **DR-4.** 페르소나 생성·메시지 분석 시 **입력한 대화 텍스트가 Google Gemini API로 전송**됨을 고지한다. 타인의 대화·민감정보 입력에 대한 주의도 함께 적는다. 기본안은 온보딩 모달이며, 노출 위치·문구 수준은 P2 온보딩 문구 작성 시 확정한다(§11).
  - **두 화면이 보내는 것은 서로 다르다.** **페르소나 생성**은 대화 **텍스트만** 보낸다 — 붙여넣은 것이든 .txt 파일에서 채운 것이든, 전송되는 것은 입력란에 보이는 그 텍스트다(파일이 통째로 올라가지 않는다). **메시지 분석**은 대화 텍스트 **또는 첨부한 캡처 이미지**를 보낸다(FR-39).
  - **캡처를 보내는 경로는 이제 분석 탭 하나뿐이다.** 캡처에는 대화 본문 외에 프로필 사진·표시 이름·읽음 표시 같은 **부수 정보가 함께 담기며 그대로 Google로 나간다.** 온보딩 동의 문구는 그대로 두고, **분석 탭 이미지 모드 힌트에** 이 사실을 한 줄로 적는다([DESIGN §6.1](./DESIGN.md)). 페르소나 생성 시트에는 캡처 모드가 없으므로 그 줄이 필요 없다.
  - 설정 탭 고지(FR-38 ②)의 실제 문구(`settings.privacyGemini`)는 "페르소나 생성 시 대화 텍스트나 캡처 이미지가, 분석 시 페르소나와 대화 내용이 Google Gemini API로 직접 전송됩니다"다 — P5~P9 시점의 문장이 그대로 남아 캡처를 **생성 쪽에** 붙이고 분석 쪽에서는 빼고 있어, 위 두 문단의 P10 이후 사실과 어긋난다(P11 코드 대조에서 발견). FR-38 ②의 요구대로 고치는 것은 후속이다(§11.2, [PLAN §8.3](./PLAN.md) #4). 같은 카드의 ③(`settings.privacyKey`)도 FR-38 ③에 없는 "HTTP referrer를 littleanti.github.io로 제한" 권고를 담고 있어 함께 정정 대상이다 — `no-referrer` meta(NFR-7 / [TRD §8.1](./TRD.md)) 때문에 이 앱은 Referer를 보내지 않으므로, 그 제한을 걸면 Gemini 호출이 거부된다.
- **DR-5.** 키·대화·프롬프트·LLM 응답을 **콘솔이나 서버 로그에 남기지 않는다.**
- **DR-6.** 사용자는 앱 안에서 **개별 페르소나·개별 기록·API 키**를 삭제할 수 있고, 설정 탭에서 **전체 로컬 데이터를 한 번에** 지울 수 있다(FR-37). 브라우저 사이트 데이터 삭제 시 모든 로컬 데이터가 사라지고 복구 수단이 없음을 고지하며, 그 대비 수단으로 백업 내보내기·가져오기를 제공한다(FR-35·FR-36). 스레드 드래프트(DR-1)는 입력란을 비우면 함께 지워지고 전체 삭제에도 포함되며, 페르소나별 전용 삭제 UI는 따로 두지 않는다(§11).
- **DR-7.** AI가 만든 페르소나와 답변 후보는 **참고용**이며 심리 진단이나 관계 결정을 대신하지 않음을 고지한다(노출 위치는 FR-38).
- **DR-8.** **백업 파일에는 API 키를 넣지 않는다.** 내보내는 것은 페르소나·분석 기록·스레드 드래프트뿐이고, 키는 사용자가 새 브라우저에서 다시 입력한다. 백업은 사용자가 파일 시스템·클라우드·메신저로 옮길 수 있어 **브라우저 밖으로 나가는 유일한 산출물**이며, 여기에 키가 섞이면 §8이 지키려는 "키는 이 브라우저에만"이 저장 매체와 무관하게 다시 깨진다. 대화 원문이 백업에 들어가는 것은 그 자체가 백업의 목적이므로 감수하고, 파일 취급 주의는 고지로 다룬다(FR-38).

## 6. 비기능 요구사항 (NFR)
- **NFR-1. 모바일 우선.** 콘텐츠 최대 폭 `max-w-2xl`(672px) 중앙 정렬, 하단 탭바는 `max-w-lg`(512px) 중앙 고정, 터치 가능한 버튼 크기. 모바일(≤640px)에서는 두 값이 화면 폭과 같아 차이가 없고, 데스크톱에서는 페르소나 항목 카드·대화 입력란이 조금 더 넓게 놓인다(P3에서 `max-w-lg`→`max-w-2xl`로 조정).
- **NFR-2. 정적 산출물.** TypeScript strict, `npm run build` = `tsc --noEmit` + `vite build` → `dist/`. 런타임 Node 20+(빌드·미리보기 서버 기준).
- **NFR-3. 응답 지연.** 단일 모델 `gemini-3.1-flash-lite`에 `thinkingConfig.thinkingBudget=0`을 적용해 추론 토큰을 제거하고, 텍스트 요청 타임아웃은 60초로 둔다. M1까지의 실키 실측(각 1회, 브라우저 Resource Timing — [LOG](./LOG.md) P2~P4): 소형 프롬프트 1.94s / 페르소나 생성 6.57s·5.87s / 메시지 분석 3.49s. 모두 60초 타임아웃 안이다. **thinking off 자체의 효과는 미실측** — off 상태의 지연만 쟀고 on 상태와 비교하지 않았다(§11).
  - **캡처 이미지가 붙은 요청은 타임아웃을 180초로 따로 둔다.** 인라인 base64 페이로드가 텍스트 프롬프트보다 훨씬 크고 이미지 판독이 함께 일어나므로 60초로는 조기 실패할 수 있다고 보기 때문이다. 실측은 각 표본 1건뿐이다 — 캡처 1장 페르소나 생성 4.95s(P5), 캡처 1장 분석 2.75s(P9). 둘 다 180초에 한참 못 미치므로 값은 그대로 두되, **여유값이라는 성격은 그대로다**(§11). **P10 이후 이 타임아웃이 적용되는 경로는 분석 탭 하나뿐이다** — 페르소나 생성은 텍스트 전용이 되어 항상 60초를 쓴다.
  - **첨부한 대화 파일(.txt)은 텍스트 경로로 나간다.** 파일을 통째로 보내지 않고 말미 16,000자만 잘라 프롬프트에 넣으므로(FR-7), 요청 크기는 파일 크기와 무관하게 약 46 KB 수준으로 고정되고 타임아웃도 텍스트와 같은 60초다. P10 실측(각 1회): 상한까지 채운 15,989자 생성 **5.63s**, 머리말만 제거된 1,238자 생성 **5.57s** — 분량이 10배 차이인데 지연은 거의 같았다. 다만 표본이 각 1건이고 **토큰 사용량·품질은 재지 않았다**(§11).
- **NFR-4. 첫 로드 크기.** `@google/genai` 단일 SDK 사용, 불필요한 의존성 배제. M1 `vite build` 산출물 실측: JS 529.88 kB(gzip 131.68 kB). 같은 형태의 직전 P4 빌드에서 CSS 21.43 kB(gzip 4.80 kB), index.html 0.81 kB(gzip 0.42 kB). JS가 500 kB를 넘는 주된 원인은 `@google/genai` 번들이다. 구체 상한과 코드 스플리팅 도입 여부는 배포 단계(P8) 직전에 판단한다(§11).
- **NFR-5. 오프라인 열람.** 저장된 페르소나·기록의 열람·삭제는 LLM 호출이 없으므로 네트워크 없이 동작해야 한다(앱 셸이 로드된 상태 기준).
- **NFR-6. 브라우저 지원.** 최신 iOS Safari, Android Chrome, 데스크톱 Chrome. IndexedDB 필수.
- **NFR-7. 보안 기본기.** 사용자 입력·LLM 출력은 React 텍스트 렌더링으로만 표시한다(HTML/Markdown 렌더 금지). **CSP와 referrer 정책은 `index.html`의 meta로 적용한다** — GitHub Pages는 응답 헤더를 바꿀 수 없어 헤더가 아니라 meta가 유일한 수단이다. 허용 출처는 self와 Gemini 엔드포인트로 한정하고, 정확한 정책 문자열은 [TRD §8](./TRD.md)이 단일 출처다.
- **NFR-8. 오류 복원력.** LLM 호출 실패가 앱 전체를 멈추지 않는다. 실패는 토스트로 알리고 입력값은 유지한다.

## 8. 아키텍처 방향 결정 (3단 사고)

### 8.1 문제
대화 원문을 LLM에 넣어야 하는 제품에서 **데이터(저장) · 연산(LLM) · 서버(호스팅)** 를 어디에 둘 것인가. 제약: 운영자는 개인 1인, LLM 비용을 상시 부담하기 어렵고, 사용자 대화를 보관하는 책임을 지고 싶지 않다. 배포는 가급적 정적 호스팅(GitHub Pages)으로 끝내고 싶다.

### 8.2 1차 사고 — 후보와 첫 결론
| 후보 | 데이터 | 연산 | 서버 | 첫인상 |
|---|---|---|---|---|
| (a) 서버 + 로컬 Ollama | 서버 디스크(JSON) | 서버의 로컬 LLM | 상시 앱 서버 + GPU | 외부 API 의존 없음, 비용 0에 가까움 |
| (b) 서버 프록시 + 운영자 키 | 서버 DB 또는 브라우저 | 서버가 운영자 키로 Gemini 호출 | 상시 API 서버 | 사용자가 키를 몰라도 됨, 온보딩 마찰 최소 |
| (c) Client-First | 브라우저 IndexedDB | 브라우저가 **사용자 키**로 Gemini 직접 호출 | 정적 파일만 | 서버 부담·비용·보관 책임 모두 0 |

1차 결론: **(c) Client-First.** (a)는 "사용자마다 서버와 GPU가 필요"해 배포 가능한 제품이 되지 않고, 대화가 서버 디스크에 남는다. (b)는 운영자 비용이 사용자 수에 비례하고, 대화가 운영자 인프라를 경유·보관될 수 있어 §1의 원칙과 충돌하며, 정적 호스팅이 불가능하다.

### 8.3 비판적 재사고 — (c)를 공격한다
| 공격 | 검토 | 결과 |
|---|---|---|
| **키가 브라우저에 있다(XSS 시 유출).** 서버 보관보다 위험하지 않은가? | 브라우저 JS가 Gemini를 직접 호출해야 하므로 키는 JS에서 읽을 수 있어야 한다(HttpOnly 불가). 이건 (c)의 구조적 비용이다. 완화는 두 층이다 — **주입 경로 차단**: 사용자·LLM 출력은 React 텍스트 렌더링만, 의존성 최소화, CSP(P8), 콘솔 미출력. **피해 범위 축소**: 키를 Gemini API(Generative Language API)만 쓰도록 제한하고 노출 의심 시 회전하도록 안내. HTTP referrer 제한은 AI Studio에서 가능한지 미확인이고, 성립해도 우리 origin에서 실행되는 XSS는 같은 referrer로 통과하며 탈취 후 비브라우저 클라이언트는 Referer를 임의로 넣을 수 있어 **효과가 제한적**이다. 키는 **사용자 소유**라 유출 시 피해 범위도 사용자 본인 키에 한정된다. | 살아남음(완화책 채택, 리스크 R1로 관리) |
| **사용자가 직접 키를 발급해야 한다.** 온보딩 마찰이 크지 않은가? | 대상 사용자를 "API 키를 발급받을 수 있는 사용자"로 명시(§2.1)하고, 발급 링크와 체크박스만으로 단순화한다. (b)로 마찰을 없애면 §1 원칙과 비용 구조가 무너진다. 이 트레이드오프는 의도적으로 감수한다. | 살아남음(대상 사용자 정의로 흡수) |
| **브라우저에서 Gemini를 직접 호출할 수 있는가(CORS)?** | `@google/genai`는 브라우저 사용을 지원하는 SDK다. CORS 통과 여부와 SDK 오류 객체의 형태는 **실키 없이도 확인할 수 있다** — 임의(무효) 키로 1회 호출하면 요청이 Google에 도달할 경우 인증 오류(400/403)가 SDK 오류로 돌아오고, CORS 차단이면 `Failed to fetch`/TypeError가 온다. P2에서 이 호출을 실행해 결과를 LOG에 기록하고, 실행하지 않았으면 미실행으로 남긴다. 실키가 필요한 항목은 품질·지연만이다. SDK 파손·브라우저 번들 미지원에 대비해 호출은 한 모듈에 캡슐화한다(REST 폴백은 R2a). | 살아남음(미확정 — P2 임의 키 호출로 확인) |
| **브라우저 데이터는 사라진다.** 사이트 데이터 삭제·기기 변경 시 복구 불가 | (a)/(b)처럼 서버에 두면 해결되지만 그것이 바로 피하려는 것이다. 고지(DR-6)한다. 유실에 대한 추가 대응책은 실사용 후 판단한다. | 살아남음(고지로 완화) |
| **(a)를 너무 쉽게 버렸나?** 서버 저장을 암호화하면 되지 않나 | 암호화해도 "사용자마다 GPU 서버가 필요"라는 배포 장벽은 그대로다. 이 제품의 대상은 일반 사용자(§2.1)이므로 (a)는 데모 이상이 되기 어렵다. | 기각 유지 |
| **(b)를 너무 쉽게 버렸나?** 서버리스 함수로 프록시하면 정적 호스팅에 가깝지 않나 | 호스팅 형태는 해결되지만 운영자 키·비용, 대화가 운영자 인프라를 경유한다는 점, 남용 방어(레이트리밋·인증)를 운영자가 떠안는 점은 그대로다. | 기각 유지 |
| **서버가 없으니 남용을 막을 수 없다.** | 호출 비용은 사용자 본인 키로 사용자에게 귀속되므로 운영자가 방어할 대상이 없다. | 살아남음 |

### 8.4 종합 — 결정
**Client-First를 채택한다.** 개인 데이터는 IndexedDB, 키는 localStorage(부속 결정 1), LLM은 사용자 키로 브라우저 직접 호출, 서버는 정적 파일만(GitHub Pages `https://littleanti.github.io/persora/`, 개발 중에는 로컬 Express 미리보기 서버로 같은 Wi-Fi 휴대폰 테스트). 살아남은 이유는 "대안들이 해결하는 문제(온보딩 마찰·데이터 유실)가 이 제품이 지키려는 원칙(보관 책임 없음·비용 0·정적 배포)보다 작다"는 것이다. 감수하는 비용은 XSS 노출면(R1)과 온보딩 마찰이며, 둘 다 완화책이 있다.

| 기각 대안 | 기각 이유 |
|---|---|
| (a) 서버 + 로컬 Ollama | 사용자마다 상시 서버·GPU 필요, 대화가 서버 디스크에 남음 |
| (b) 서버 프록시 + 운영자 키 | 운영자 비용이 사용자 수에 비례, 개인정보가 운영자 인프라를 경유·보관, 정적 호스팅 불가 |

**부속 결정 1 — 키 저장 매체(쿠키 → localStorage, P8에서 재검토해 뒤집었다).**

*원 결정(P0) — 기록으로 남긴다*
- 1차 사고: 브라우저 쿠키 `pm_gemini_key`(1년, `SameSite=Lax`). 구현이 단순하고 새로고침·재방문에 유지되며, 만료를 선언적으로 둘 수 있다.
- 비판적 재사고: localStorage와 비교해 XSS 관점에서 더 위험한가? 둘 다 같은 origin의 JS에서 읽히므로 **XSS 관점의 노출면은 동등**하다고 판단했다(HttpOnly는 브라우저가 키를 써야 하므로 어차피 불가). 키 길이는 수십 자라 쿠키 크기 한도와 무관하다.
- 종합: **쿠키 채택.** P2에서 그대로 구현했다.

*재검토(P8 보안 점검) — 결론이 뒤집혔다*

배포는 이 앱의 데이터가 제3자 호스트를 처음 지나가는 시점이다. 그래서 P8의 첫 점검 항목을 "키가 브라우저 밖으로 나가는 경로가 있는가"로 잡고 실제로 다시 쟀다.

- **1차 사고** — 원 결정 그대로다. 쿠키로 충분하다. XSS 노출면이 localStorage와 같으니 저장 매체를 바꿀 이유가 없다.
- **비판적 재사고 — 반증을 실측했다(2026-09-05).** P0의 2차 사고는 **"XSS"라는 한 축만** 공격했고, 쿠키의 정의적 속성 — 같은 사이트로 가는 **모든 HTTP 요청에 브라우저가 자동으로 첨부한다** — 은 겨누지 않았다. 그것을 실제로 재생했다. 정적 서버(`dist/` 서빙)에 요청별 `Cookie` 헤더를 기록하는 미들웨어를 붙이고(키 값은 남기지 않고 이름·길이만), 새 브라우저 프로필로 접속해 온보딩에서 키를 저장한 뒤 새로고침과 자산 요청을 냈다.

  | 시점 | 서버가 받은 요청 | 그중 키 쿠키가 실린 요청 |
  |---|---|---|
  | 키 저장 전 | 4건 | **0건** |
  | 키 저장 후 | 5건 | **5건** — `/`, `assets/index-*.js`, `assets/index-*.css`, `app-logo.png`(2회) |

  정적 자산 요청이 **한 건도 빠짐없이** 사용자 키를 서버로 실어 보냈다. 즉 GitHub Pages 같은 제3자 정적 호스트도 **매 요청마다 사용자 키를 수신하며, 접근 로그에 남을 수 있다.** 이 결과는 두 서술을 거짓으로 만든다 — 온보딩 문구 "키와 모든 데이터는 이 브라우저에만 저장되며 서버로 전송되지 않습니다", 그리고 DR-2·DR-3("우리 서버로 가는 요청은 정적 자산 요청뿐"). 쿠키를 유지한 채로 막을 방법도 없다: `SameSite`는 **교차 사이트** 요청을 막는 것이라 같은 사이트인 우리 자산 요청은 그대로 통과하고, `HttpOnly`는 JS가 키를 읽어 Gemini를 불러야 하므로 애초에 쓸 수 없다. 반면 localStorage 값은 어떤 요청에도 자동으로 실리지 않으며, XSS 노출면은 P0이 판단한 그대로 쿠키와 **동등**하다(둘 다 같은 origin JS가 읽는다).
- **종합.** API 키 저장소를 **localStorage `pm_gemini_key`로 전환한다.** 살아남은 근거는 하나다 — 두 매체의 XSS 노출면은 같은데, 쿠키에만 "매 요청 자동 전송"이라는 추가 노출 경로가 붙어 있고 그것을 끌 수단이 없다. 개발 기기 브라우저에 남은 쿠키는 **최초 읽기에서 한 번 localStorage로 옮기고 쿠키를 만료시킨다**(공개 배포 전이라 실제 사용자 데이터는 없지만, 잔존 쿠키는 계속 요청에 실리므로 지우는 편이 맞다). 온보딩·설정 고지 문구도 사실대로 고친다 — "키와 데이터는 이 브라우저(localStorage/IndexedDB)에 저장되고, 생성·분석 시 입력한 대화와 키는 Google로 직접 전송된다".

  남기는 교훈은 매체 선택이 아니라 **2차 사고의 사각**이다. P0의 비판적 재사고는 "localStorage보다 위험한가"라는 **비교 축 하나**만 세웠고, 그 축에서는 정말로 동등했다. 놓친 것은 비교가 아니라 **쿠키 단독의 속성**이었다. 앞으로 저장 매체·전송 경로를 고를 때는 "대안보다 나쁜가"와 함께 "이 매체가 스스로 하는 일이 무엇인가"를 따로 물어야 한다.

**부속 결정 2 — 모델.**
- 1차 사고: `gemini-3.1-flash-lite` 단일 모델 + `thinkingBudget=0`. flash 계열 중 thinking을 끌 수 있어 단건 지연을 줄일 수 있고(문헌 근거 — 지연 단축 효과는 미실측), 멀티모달이라 P5의 캡처 이미지 입력도 같은 경로로 처리 가능하다.
- 비판적 재사고: ① lite 모델이 한국어 대화의 뉘앙스 분석에 충분한가? thinking을 끄면 분석 깊이가 떨어지지 않는가? — 프롬프트가 필드·후보 구조를 강하게 지정하므로 자유 추론 의존도는 낮다고 가정하지만, **품질·지연 모두 키가 있어야 측정 가능**하다. ② 왜 lite인가? 비-lite flash도 thinking을 끌 수 있다. lite를 고른 근거(비용·무료 할당량·지연)는 실측이 없어 **선택 근거 미확정**이다. ③ 모델명과 `thinkingConfig` 자체가 API에서 수락되는지도 미확인이다.
- 종합: 채택하되 모델명·thinking 설정은 설정 파일 한 곳에서 관리해 실측 후 교체 가능하게 한다. P3~P4 실사용에서 품질 문제가 보이면 비-lite flash가 교체 후보다. 품질·지연·모델명 유효성은 미확정(§11).

**부속 결정 3 — 페르소나 생성의 대화 입력(캡처 이미지 → 카카오톡 대화 파일 첨부, P10에서 재검토해 뒤집었다).**

*원 결정(P5) — 기록으로 남긴다*

- **1차 사고.** 텍스트 붙여넣기만으로는 넣을 수 없는 대화가 있다. ① 내 기기가 아닌 화면(상대가 보여준 대화, 지인의 상담 요청), ② 복사 기능이 막혔거나 이미 지운 대화, ③ 스크롤하며 캡처만 떠 둔 대화. 캡처는 사용자가 이미 습관적으로 만드는 산출물이라 입력 마찰도 낮다. 모델이 멀티모달이므로 별도 OCR 없이 같은 호출 경로에 이미지를 얹을 수 있다(부속 결정 2). → 캡처 이미지 입력을 추가한다.
- **비판적 재사고 — 이 결론을 공격한다.**

  | 공격 | 검토 | 결과 |
  |---|---|---|
  | **페이로드가 무겁다.** 스크린샷은 텍스트 프롬프트와 비교가 안 되게 크고, base64로 실으면 원본 바이트보다 약 4/3로 더 늘어난다(인코딩 특성). 여러 장이면 요청이 커져 느려지거나 타임아웃에 걸릴 수 있다 | 이미지 경로에만 180초 타임아웃을 따로 둬 조기 실패를 막는다(NFR-3). 다만 **장당 실제 크기도, 요청 지연도 아직 재지 않았다** — 180초는 근거 없는 여유값이다. P5 검증에서 실제 캡처로 지연을 실측한다 | 살아남음(완화책 채택, 수치는 미확정) |
  | **정보량이 텍스트보다 적을 수 있다.** 캡처 한 장에는 화면 한 장 분량의 메시지만 담긴다. 페르소나 품질은 인용할 발화가 얼마나 많은지에 좌우되는데(FR-8), 캡처 몇 장이 붙여넣기 한 번을 대체하지 못할 수 있다 | 반박하지 못했다. 장수를 늘리면 분량은 늘지만 그만큼 페이로드도 커진다. **텍스트 대비 페르소나 정확도는 미확정** — 표본이 없다. 실사용에서 관찰한다(§11) | **반증 못 함 — 미확정으로 남김** |
  | **캡처는 대화 본문만 담고 있지 않다.** 프로필 사진·표시 이름·다른 대화방 미리보기 같은 부수 정보가 함께 Google로 나간다 | 사실이다. 막을 방법은 사용자가 캡처 범위를 조절하는 것뿐이다. 고지로 다룬다(DR-4) | 살아남음(고지로 완화) |
  | **텍스트 모드를 대체하면 되지 않나** | 위 두 번째 공격이 미확정으로 남은 이상 검증된 입력 경로를 버릴 근거가 없다. 텍스트가 가능한 상황에서 캡처를 강요하면 정보량이 줄어들기만 한다 | **대체 기각** |
  | **M1 안에 넣지 않은 것이 늦은 판단 아닌가** | 아니다. 이미지 경로는 파일 읽기·base64 인코딩·페이로드 크기·긴 타임아웃·드롭존 UI라는 별도 실패 표면을 가진다. M1을 텍스트 전용으로 닫았기에 지금 실패가 나면 원인이 이미지 경로라고 바로 말할 수 있다([PLAN §6](./PLAN.md)) | 순서 유지 |

- **종합.** 텍스트 붙여넣기를 **기본 모드로 두고**, 캡처 이미지는 **선택 모드로 추가한다.** 살아남은 근거는 "텍스트로는 아예 넣을 수 없는 대화가 존재한다"는 것 하나이고, 이는 정확도와 무관하게 성립한다. 정확도(캡처 vs 텍스트)와 이미지 요청 지연은 **둘 다 미확정**이며 관찰 항목으로 남긴다(§11). 이미지 경로는 기존 텍스트 계약에 **선택 필드를 가산**하는 방식으로만 붙여, 실패 시 이미지 관련 코드만 되돌리면 텍스트 경로가 그대로 남게 한다. — P5에서 그대로 구현했다.

*재검토(P10 페르소나 입력 재평가) — 결론이 뒤집혔다*

- **문제 제기(P5 실사용 관찰).** 원 결정이 **미확정으로 남겨 둔 항목**이 실사용에서 신호를 냈다. 캡처 1장으로 만든 페르소나는 `vocabulary_examples` 5개 중 2개가 음식 이름("쿡밥", "설렁탕")이라 말투 지표가 아니었다. 같은 프롬프트로 텍스트 38줄(1,331자)을 넣었을 때는 6개가 모두 어미·감탄 표현이었다([LOG](./LOG.md) P5, 각 표본 1). 원 결정의 2차 사고에서 **반증하지 못한 채 살아 있던 지적** — "캡처 한 장은 화면 한 장 분량의 발화만 담아 인용 재료가 적을 수 있다" — 과 방향이 같다.

- **1차 사고.** 캡처 모드는 그대로 두고 안내로 보완하면 된다. 힌트에 "여러 장을 시간 순서대로 올리면 더 정확해요"라고 이미 적어 두었으니, 사용자가 여러 장을 올리면 분량 문제는 사라진다.

- **비판적 재사고 — 계산하고 실측치를 대조했다.** 다섯 갈래로 공격했다.

  ① **분량이 정확도를 좌우한다는 것은 프롬프트가 스스로 말한다.** 페르소나 프롬프트는 `vocabulary_examples`·`sentence_style`·`texting_habits`에 **실제 발화를 그대로 인용**하라고 강제한다(FR-8). 인용할 발화가 적으면 채울 것이 없어 눈에 띄는 명사라도 집어넣게 된다 — P5 관찰이 정확히 그 모습이다. 그렇다면 물어야 할 것은 "캡처가 편한가"가 아니라 **"어느 입력이 발화를 더 많이 담는가"** 다.

  ② **두 입력의 분량과 페이로드를 실제로 계산했다.** 샘플 카카오톡 대화 텍스트는 1,331자에 메시지 34줄, **평균 32.6자/메시지**다. 캡처 한 장이 담는 것은 화면 한 장 분량(약 10~15개 말풍선 — **추정이며 OCR로 세지 않았다**)이다.

  | 입력 | 담기는 메시지 | 전송 페이로드 | 실측 지연(표본 1) |
  |---|---|---|---|
  | 캡처 이미지 1장 | 화면 한 장 분량 **약 10~15개**(추정) | 원본 JPEG 648×1440, 162,080 B → base64 **약 211 KiB**(= 216 kB; P5·P9 LOG의 "216 kB"와 같은 값) | 4.95s(P5) |
  | 대화 .txt 말미 16,000자 | 평균 32.6자/메시지 기준 **약 490개** | UTF-8 **약 46 KB** | 텍스트 1,331자 생성이 6.57s(P3) |

  담는 메시지 수는 **두 자릿수 차이**이고, 그런데도 페이로드는 이미지가 **약 4.5배 무겁다.** 무거운 쪽이 적게 담는다 — 이 방향의 트레이드오프에는 변호할 여지가 없다. 캡처 경로에 180초 타임아웃을 따로 둔 것(NFR-3)도 이 무게 때문이었다.

  ③ **"여러 장 올리기"는 사용자에게 비용을 떠넘기는 답이다.** 490개 메시지를 캡처로 채우려면 스크롤과 캡처를 수십 번 반복해야 하고, 그만큼 페이로드도 함께 커진다. 반면 카카오톡은 **대화 전체를 .txt로 내보내는 기능을 이미 제공한다** — 사용자가 파일 하나를 고르면 수천 줄이 한 번에 들어온다. 1차 사고의 "안내로 보완"은 앱이 할 일을 사용자에게 미루는 것이었다.

  ④ **그러면 분석 탭의 캡처 모드(부속 결정 5)도 함께 버려야 하는가? 아니다.** 두 화면이 필요로 하는 분량이 다르다. 페르소나는 말투 지문을 뽑는 **장기 표본**이라 많을수록 좋고, 분석은 마지막 메시지에 답하기 위한 **단기 맥락**이라 화면 한 장 분량이 오히려 맞는 크기다(부속 결정 5의 두 번째 공격). 같은 기술을 한 화면에서는 버리고 다른 화면에서는 유지하는 근거가 이것이다 — 기술의 문제가 아니라 **그 화면이 필요로 하는 분량**의 문제다.

  ⑤ **반증하지 못한 것 — 정확도 차이 자체는 여전히 표본이 없다.** 같은 대화를 캡처로 한 번, .txt로 한 번 넣어 나온 페르소나를 나란히 비교한 표본은 없다. 위 판단의 근거는 **계산(분량·페이로드)과 P5의 단발 관찰**이고, "16,000자가 캡처 1장보다 정확한 페르소나를 만든다"는 것은 **정성 판단**이다. 미확정으로 남긴다(§11).

- **종합.** 페르소나 생성의 **캡처 이미지 모드를 제거하고**, 대화 텍스트 단일 흐름 + **카카오톡 대화 파일(.txt) 첨부**로 교체한다(FR-7). 살아남은 근거는 ②의 비대칭 하나다 — **더 무거운 입력이 더 적게 담는다.** ③은 그 비대칭을 사용자 손으로 메우려는 시도가 이미 존재하는 기능(대화 내보내기)보다 나쁘다는 것을 보여 준다. 첨부한 파일은 머리말을 떼고 말미 16,000자만 잘라 입력란을 채우며(최근 대화일수록 지금의 말투·관계를 반영한다), 사용자는 그 결과를 편집할 수 있고 얼마나 쓰였는지 안내를 본다.

  **버리는 것을 명시한다.** 텍스트로 아예 넣을 수 없는 대화 — 타인 기기의 화면, 복사가 막힌 대화 — 는 이제 페르소나 생성에 넣을 수 없다. 그것이 원 결정의 유일한 생존 근거였고, P10은 그 근거보다 ②의 비대칭이 크다고 판단한 것이다. 되돌릴 여지는 남겨 둔다: 멀티모달 호출 경로(`generate(prompt, images)`)와 파일→인라인 이미지 변환기는 분석 탭이 계속 쓰므로 코드에 그대로 남는다([TRD ADR-10](./TRD.md)).

  **남기는 교훈은 두 가지다.** 첫째, P5 문서가 정확도를 **"반증 못 함 — 미확정"** 으로 정직하게 남겨 둔 것이 옳았다. 그 자리에 "괜찮을 것"이라고 적어 두었다면 P5 관찰이 신호로 읽히지 않았을 것이다. 둘째, **관찰 결과로 자기 결정을 뒤집는 것이 이 워크플로의 정상 경로다** — 부속 결정 1(P8)에 이은 두 번째 사례이며, 두 번 다 뒤집은 근거는 새 취향이 아니라 **재서 얻은 수치**였다.

**부속 결정 4 — 분석의 입력 계약을 재설계한다(최근 대화 스레드 + 답장 대상 + 답장 의도).**

- **문제 제기(M1 실사용 리뷰).** 제품 의도는 "① 과거 대화로 상대의 장기 페르소나를 파악하고 → ② 최근 대화 맥락에서 → ③ 상대의 **마지막 메시지**에 **내 의도**대로 답장"이다(§1). v1에는 ①과 ③의 일부만 있고 **②가 입력 계약에 아예 없었다.** 근거는 코드다 — 기록 레코드의 분석 대상이 `message: string`(메시지 1건)이고, 분석 프롬프트가 `{ persona, message }`를 받아 "…가 **다음 메시지를 보냈습니다**"로 **단발 메시지를 전제**하며, 화면 라벨은 "받은 메시지", 답장 의도를 넣을 자리가 없어 후보 3개가 항상 공감 3축에 고정돼 있었다.

- **1차 사고.** v1으로 충분하다. 사용자가 textarea에 최근 대화를 여러 줄 붙여 넣으면 모델이 알아서 맥락을 읽을 것이다. 구조를 바꿀 필요가 없다.

- **비판적 재사고 — 반증을 실측했다.** "스레드를 통째로 넣으면 품질이 무너진다"가 사실인지 실제로 재생했다. 2026-09-05, 유효 키, 분석 함수를 직접 호출(페르소나 지수/현우).

  | 변형 | 입력 | 지연 | 결과 |
  |---|---|---|---|
  | A | 최근 대화 스레드 6줄, **상대 발화로 끝남** | 3.52s | 분석과 후보 3개가 상대의 마지막 고민("리드 맡아보라는데… 너는 어떻게 생각해?")에 정확히 답했다 |
  | B | 같은 스레드 + 마지막 줄이 **내 발화**("일단 축하해! 근데 부담되는 건 당연하지") | 3.84s | 그래도 분석·후보는 상대의 고민에 답했다 — 모델이 관대하게 처리했다 |

  **"품질이 무너진다"는 공격은 이 표본(2건)에서 반증됐다.** 1차 사고의 "모델이 알아서 읽는다"는 절반은 맞다. 그러나 살아남은 문제가 셋이다.

  | 살아남은 문제 | 내용 |
  |---|---|
  | (a) **앱이 답장 대상을 모른다** | 변형 B에서 내 발화까지 "받은 메시지"로 저장·표시됐다. UI는 어느 메시지에 답하는지 보여 주지도, 고치지도 못한다. 모델이 알아서 맞혀 준다는 것과 앱이 안다는 것은 다르다 |
  | (b) **답장 의도 슬롯이 없다** | 후보 세 개가 공감·해결·전환 축에 고정되어 거절·선 긋기·설득 같은 목표를 낼 수 없다. ③의 "내 의도대로"가 통째로 빠져 있다 |
  | (c) **프롬프트가 거짓 전제를 깐다** | "다음 메시지를 보냈습니다"에 여러 화자의 스레드를 넣는 것은 계약 위반이다. 지금 통하는 것은 모델의 관대함이지 설계가 아니며, 표본 2건으로 관대함이 계속되리라 단정할 수도 없다 |

- **종합.** 재설계는 **품질 붕괴 때문이 아니라 입력 계약을 사실대로 만들기 위해** 한다. 새 입력은 **페르소나(장기) + 최근 대화 스레드(단기 맥락) + 답장 의도**다. 스레드는 파서가 화자를 구분해 상대의 마지막 발화를 답장 대상으로 자동 검출하고 화면에 표시하며, 틀리면 사용자가 고른다(FR-29·FR-30). 의도는 프리셋 6종 + 직접 입력이고 **비워 두는 것이 기본값**이라, 의도를 넣지 않으면 v1과 같은 공감 3축이 그대로 나온다(FR-31) — 반증에서 살아남은 v1의 동작을 버리지 않기 위한 무회귀 장치다.

  함께 정한 **비목표**는 두 가지다. **페르소나 자동 갱신(N6)** — 분석마다 페르소나를 다시 계산하면 매 호출 비용·지연이 늘고 "어느 시점 페르소나로 만든 답인지"가 흔들린다. 정적으로 두고 사용자가 "추가 대화로 업데이트"(FR-28)를 직접 누르게 한다. **앱 내 대화 누적(N7)** — 대화를 이어서 보관하면 이 앱이 또 하나의 메신저 저장소가 되어 §1의 보관 책임 원칙과 충돌한다. 매번 붙여넣되 페르소나별 드래프트 자동 저장(FR-32)으로 재입력 부담만 낮춘다.

  남은 미확정: 의도 지정이 실제로 후보 방향을 바꾸는지는 **아직 실측하지 않았다**(§11). 위 표본 2건은 v1 코드에서 잰 것이고, 재설계 후의 의도 스티어링은 별도로 확인해야 한다.

**부속 결정 5 — 메시지 분석에도 캡처 이미지 입력을 더한다(선택 모드).**

- **문제.** 분석 탭은 최근 대화 스레드를 **텍스트로 붙여 넣어야만** 동작한다(FR-12). 페르소나 생성에는 캡처 이미지 모드가 있는데(부속 결정 3) 분석에는 없다. 같은 사용자가 같은 대화 앱에서 같은 제약을 만나는데 한쪽 화면에만 우회로가 있는 상태다.

- **1차 사고.** 분석은 붙여넣기로 충분하다. 여기서 넣는 것은 "최근 대화 몇 줄"이고, 페르소나 생성에 넣는 수백 메시지와 달리 짧다. 카카오톡에서 몇 줄 복사하는 것은 어렵지 않다. 게다가 이미지 모드를 열면 파서·타겟 칩·드래프트가 통째로 동작하지 않는 두 번째 경로가 생긴다.

- **비판적 재사고 — 이 결론을 공격한다.**

  | 공격 | 검토 | 결과 |
  |---|---|---|
  | **"몇 줄 복사"가 실제로는 손이 많이 간다.** 휴대폰 카카오톡에서 여러 말풍선을 가져오려면 말풍선을 길게 눌러 선택 모드로 들어가 하나씩 체크하고 복사해야 한다. 반면 캡처는 버튼 조합 한 번이다. 주 사용 환경이 모바일(§2.1)인 제품에서 입력 마찰의 차이가 작지 않다 | 반박하지 못했다. 텍스트 붙여넣기가 언제나 더 싸다는 전제가 모바일에서는 성립하지 않는다 | **1차 사고의 전제가 깨짐** |
  | **부속 결정 3에서 미확정으로 남은 "분량 부족"이 여기서는 문제가 아니다.** 캡처 한 장은 화면 한 장 분량인데, 분석이 필요로 하는 단기 맥락이 정확히 그 크기다(최근 몇 줄). 장기 페르소나와 달리 인용 재료를 많이 모을 이유가 없다 | 성립한다. 부속 결정 3의 반증 실패 항목(캡처 정확도)이 이 화면에는 같은 강도로 적용되지 않는다 — 다만 이것도 **표본으로 확인한 것은 아니다** | 살아남음(근거는 논리, 실측 아님) |
  | **이미지 모드에서는 앱이 답장 대상을 모른다.** 텍스트가 없으니 `thread.ts` 파싱을 할 수 없고, 그래서 "이 메시지에 답장" 칩(FR-29)도 수동 교정(FR-30)도 렌더할 수 없다. 모델이 말풍선의 좌/우 위치와 순서만 보고 마지막 상대 메시지를 판별해야 하며, **오판해도 사용자가 고칠 수단이 없다** | 반박하지 못했다. 이것은 부속 결정 4가 v1을 재설계하며 되찾은 바로 그 성질("앱이 답장 대상을 안다")을 이 모드에서만 다시 내려놓는 것이다. 완화책은 프롬프트가 "맨 아래(최신) 상대 메시지에 답장"을 못 박는 것뿐이고, 그 적중률은 **표본이 없다** | **반증 못 함 — 미확정으로 남김(R10)** |
  | **지연이 더 나빠지지 않나.** 인라인 base64 페이로드는 텍스트 프롬프트보다 훨씬 크다 | P5 실측에서 캡처 1장 페르소나 생성이 4.95s로 텍스트 생성(6.57s)과 같은 자리수였다([LOG](./LOG.md) P5). 분석 프롬프트는 페르소나 프롬프트보다 짧으므로 같은 자리수를 기대하지만, **분석 경로의 이미지 요청은 재 본 적이 없다** | 살아남음(수치는 미확정) |
  | **텍스트 모드를 대체하면 되지 않나** | 세 번째 공격이 미확정으로 남은 이상 기각한다. 텍스트 모드는 앱이 답장 대상을 알고 사용자가 고칠 수 있는 유일한 경로이며, 드래프트 복원도 거기에만 있다 | **대체 기각** |

- **종합.** 분석 탭에 **텍스트/캡처 이미지 토글을 더한다**(FR-39). 텍스트가 기본이고, 이미지는 선택 모드다. 살아남은 근거는 부속 결정 3과 같은 형태다 — "텍스트로는 넣기 번거롭거나 아예 넣을 수 없는 대화가 있다"는 것 하나이며, 이는 정확도와 무관하게 성립한다. 여기에 이 화면 고유의 근거가 하나 더 붙는다: 분석이 필요로 하는 것은 **화면 한 장 분량의 단기 맥락**이라, 부속 결정 3에서 미확정으로 남았던 "분량 부족" 지적이 같은 무게로 적용되지 않는다.

  버리는 것은 명시한다. 이미지 모드에서는 앱이 답장 대상을 모르고, 그래서 타겟 칩·수동 교정·스레드 드래프트가 동작하지 않는다. 이 셋은 **텍스트 모드 전용**으로 못 박는다(FR-29·FR-30·FR-32). 모델이 답장 대상을 오판할 확률은 **반증하지 못했고 표본도 없다** — 미확정 관찰 항목으로 남긴다(§11, R10). 분석 경로의 이미지 요청 지연도 미실측이다.

  계약은 부속 결정 3과 같은 방식으로 **가산만** 한다 — 분석 입력에 선택 필드(`images?`)를, 프롬프트에 분기 플래그 하나를 더한다. 실패하면 이미지 관련 코드만 되돌리면 P6~P8의 텍스트 경로가 그대로 남는다.
